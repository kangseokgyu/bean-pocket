## Required findings, in priority order

1. **[P1] Record first-page hydration introduces a large blocking N+1 regression.** `pwa/data/read-repository.mjs:530`, `:580`, `:485-495`. `listRecords(limit:20)` assembles 40 candidates, then awaits every candidate's distinct bean and recipe page before taking the first 20. There is no parent cache between calls. With 40 distinct bean and recipe references, this is 80 serialized, paced GETs plus three schema reads and a raw query. Under the same fixture and 100ms per response, `/records` first data regresses from **6,112ms / 58 requests** to **28,872ms / 84 requests**, although only 20 records render. This also delays selected recipe/bean detail behind record hydration. Select/filter the visible page before unnecessary parent hydration, avoid blocking first display on every parent, and apply revision-scoped parent reuse or another bounded hydration strategy. Add a diverse-parent first-page budget test. Evidence: `results/benchmark.json`, `benchmark.mjs`.

2. **[P2] Keep continuation state alive while a cached page still references it.** `pwa/data/read-repository.mjs:602` deletes `previousStateId` after consuming it, while controller first-page caches retain that cursor (`pwa/ui/controller.mjs:253-259`). Repro with 25 records: open `/records` (20), More (25), visit beans, return to records within 60s (cached 20), More → `invalid-input` / read-error, remaining five inaccessible until refresh. Both Chrome widths reproduce it. Keep immutable/replayable cursor states for the cache lifetime, or consistently invalidate/update referencing cached pages. Evidence: `results/browser-extended.json` (`cacheReplay`), first test in `critic-regressions.test.mjs.txt`.

3. **[P2] Pass the query into option rendering and preserve it through rerenders.** `pwa/ui/controller.mjs:334`, `:343`; `pwa/ui/view.mjs:576`, `:626`. Both controller branches omit `setSearchOptions`'s fifth `query` argument, so the view defaults it to `''` and clears the input as soon as results arrive. More then submits that empty query with a cursor bound to the original search and fails validation. With 26 synthetic beans named `Search Ethiopia …`, searching `Search` shows 20 matches plus placeholder, clears the input, and More remains at 21 options with read-error. Reproduced at both widths. Supply query on fresh and cached results, retain the query when reconstructing the picker, and cover actual search → More after an unrelated rerender. Evidence: `results/browser-extended.json` (`search`), first test in `critic-controller.test.mjs.txt`.

4. **[P2] Resume pending work for previously visible cards after More aborts the old route generation.** `pwa/ui/controller.mjs:241`, `:262`, `:293-297` (same issue for counts at `:278-282`). Clicking More while first-page stage validation is in flight aborts its signal. The new generation starts deferred work only for the newly fetched page, while merged first-page cards remain `validationStatus:'checking'` indefinitely. Recording/copy actions remain disabled. The controlled abort test ends with `['checking','ready']` instead of both ready. Bean counts have the same loading-state lifecycle. Restart unresolved work for all currently visible cards in bounded batches, or preserve same-route work with safe generation handling. Test both summaries and counts with More during a delayed scan. Evidence: second test in `critic-controller.test.mjs.txt`, `results/controller-regressions.tap`.

5. **[P2] Merge filtered and snapshot-fallback streams in global sort order before emitting pages.** `pwa/data/read-repository.mjs:540-555`, `:585-592`. Each call takes the next direct-relation page before buffered raw fallback rows; leftover direct candidates are then prepended to pending raw rows. With 60 newer snapshot-only records and 40 older direct-relation records, all matching the same recipe, page one covers Oct 26–Oct 7, but page two starts **Aug 27**, while Oct 6 remains queued. The UI jumps older and later inserts newer records on subsequent More clicks. Sorting only the current 40 candidates does not produce the required descending continuation. Maintain ordered stream/buffer state and emit only a known next prefix. Evidence: second test in `critic-regressions.test.mjs.txt`, `ORDER` line in `results/regressions.tap`. This is an ordering finding; no unsupported claim of permanent row loss is made.

6. **[P2] Preserve warning-visible current records when non-snapshot metadata is damaged.** `pwa/data/read-repository.mjs:449-450`. The new generation gate requires every record property to match the full schema. Existing `assembleData()` intentionally retains a source-owned, valid bagless-v1 snapshot record with invalid rating/date metadata and exposes `invalidFields` for the UI warning. Replacing a valid record's rating property with rich_text makes `readAll()` retain one warning-visible record, but `listRecords()` returns zero and `getBeanRecordCounts()` reports exact zero. Use the existing source/snapshot/generation policy for visibility and preserve invalid-field diagnostics; do not silently drop a current record due to unrelated malformed display metadata. Evidence: third test in `critic-regressions.test.mjs.txt`, `DAMAGED` line in `results/regressions.tap`.

## Same-fixture baseline comparison

One bounded run per screen/version, deterministic dataset and delay; production scheduler settings retained. 60 beans, 40 recipes with 120 globally unique stages, 1,000 valid current records referencing 40 distinct beans/recipes, 100ms injected response delay. Baseline is exactly `c460395`, current is `72f27f5`; no legacy five-source assumption. All traffic uses an in-process fake transport, no remote requests. Metric is initialization start to the controller's first `renderData` callback (not browser paint, live phone speed, or Core Web Vitals).

| Screen | Baseline first data / requests / rows | Current first data / requests / rows |
| --- | --- | --- |
| Beans | 6,162ms / 58 / 60 | 463ms / 2 / 20 |
| Recipes | 6,156ms / 58 / 40 | 565ms / 3 / 20 |
| Records | 6,112ms / 58 / 1,000 | 28,872ms / 84 / 20 |

Current beans deferred count scan finished around 4,404ms with 13 total requests; it did not block the first callback. Recipe first callback is unvalidated summary data, intentionally followed by deferred validation. Records first callback awaits 40 bean + 40 recipe GETs; this explains the regression without needing a noisy browser timing claim. Serialized payload sizes in JSON are **JavaScript string code units**, explicitly not UTF-8 wire bytes; no transport-byte, memory, main-thread render-time or statistical variance claim is made. These controlled numbers are diagnostic evidence, not production performance guarantees.
